Infrastruktur, Arsitektur & Lebih Jauh

Bagian I membangun kosakata, latensi, persentil, throughput, utililisasi, dan mencakup optimasi tingkat database. Bagian kedua ini memperbesar ke infrastruktur: bagaimana statelessness memungkinkan horizontal scaling, bagaimana load balancer mendistribusikan lalu lintas, bagaimana database sendiri berskala dengan replika dan shard, bagaimana CDN mengalahkan fisika, bagaimana pemrosesan asinkron memangkas latensi yang dirasakan, dan bagaimana memilih antara monolit, microservice, dan serverless. Kita tutup dengan model mental yang mengikat semuanya.

01

Statelessness: Kunci Pemicunya

Horizontal scaling hanya bekerja jika instance server mana pun bisa menangani request mana pun. Begitu satu server memegang data eksklusif, objek sesi di memori, file upload di disk lokalnya, cache dalam proses, server itu menjadi istimewa. Kehilangan ia, dan Anda kehilangan data itu. Rutekan pengguna ke tempat lain, dan mereka dapat error. Ini statefulness, dan ia memecah horizontal scaling.

Statelessness adalah prinsip bahwa tidak ada satu instance server yang memegang informasi yang tidak bisa diakses instance lain. Setiap potongan state persisten, sesi, file, entri cache, record database, harus hidup di store eksternal bersama yang bisa dijangkau semua instance.

Fig 1 / Stateful servers break under horizontal scaling; stateless ones don't

Apa yang harus dieksternalkan

Tipe StateSalah (dalam proses)Benar (eksternal)
SesiDictionary di memoriRedis / database / token JWT
Upload fileFile system lokalS3, Cloudflare R2, MinIO
CacheMap di memoriRedis, Memcached, Valkey
DatabaseFile SQLite di diskPostgres (RDS), MySQL, SQLite terpusat
Background jobGoroutine/thread dalam prosesRedis queue, RabbitMQ, Kafka

Manajemen sesi stateless di Go

Go
import (
    "context"
    "github.com/redis/go-redis/v9"
    "time"
)

var rdb = redis.NewClient(&redis.Options{Addr: "redis:6379"})

// StoreSession saves session data in Redis so ANY server can read it.
func StoreSession(ctx context.Context, sessionID string, userID string) error {
    return rdb.Set(ctx, "session:"+sessionID, userID, 24*time.Hour).Err()
}

// GetSession retrieves session data, works regardless of which server
// the request lands on, because Redis is shared across all instances.
func GetSession(ctx context.Context, sessionID string) (string, error) {
    return rdb.Get(ctx, "session:"+sessionID).Result()
}

Sesi stateless di Python (FastAPI + Redis)

Python
import redis, uuid
from fastapi import FastAPI, Response, Cookie

app = FastAPI()
r = redis.Redis(host="redis", decode_responses=True)

@app.post("/login")
def login(response: Response, email: str, password: str):
    user = authenticate(email, password)
    session_id = str(uuid.uuid4())

    # Store in Redis, accessible by ALL server instances
    r.setex(f"session:{session_id}", 86400, user.id)
    response.set_cookie("session_id", session_id, httponly=True)
    return {"status": "ok"}
Thumb rule

Jika Anda tidak bisa menghapus instance server secara acak dan sistem Anda terus bekerja identik, arsitektur Anda ber-state dan akan rusak di bawah horizontal scaling. Audit setiap os.MkdirTemp, setiap map di memori, setiap penulisan file lokal.

02

Algoritma Load Balancer

Dengan banyak instance server, Anda butuh mekanisme memutuskan instance mana yang menangani tiap request masuk. Load balancer duduk di antara internet dan server Anda, menerima semua lalu lintas, dan meneruskan tiap request berdasarkan algoritma terpilih.

Round Robin

Algoritma paling sederhana: request didistribusikan dalam urutan berputar, server A, B, C, A, B, C. Ia bekerja baik saat semua server punya kapasitas setara dan semua request punya biaya kira-kira setara. Ia gagal saat biaya request bervariasi lebar: request mahal (panggilan API eksternal, tulis DB berat) bisa menumpuk semua di satu server secara kebetulan.

Weighted Round Robin

Variasi tempat server dengan kapasitas lebih menerima request proporsional lebih banyak. Jika server A punya 8 GB RAM dan server B/C punya 4 GB masing-masing, A mendapat dua kali lalu lintas. Masih buta terhadap biaya request.

Least Connections

Algoritma lebih pintar: load balancer melacak jumlah koneksi aktif di tiap server dan merutekan tiap request baru ke server dengan koneksi paling sedikit. Karena operasi mahal menjaga koneksi tetap terbuka lebih lama, server yang menangani request berat secara alami menerima lebih sedikit yang baru. Ini menyeimbangkan diri lintas beban kerja heterogen.

Fig 2 / Least connections routes away from the busy server automatically

Algoritma lain

Least Response Time menyukai server yang mengembalikan respons paling cepat, server yang sedang kesulitan mendapat lebih sedikit request. Resource-Based memantau pemakaian CPU/RAM aktual di tiap server dan merutekan sesuai. IP Hash secara deterministik memetakan tiap IP klien ke server spesifik (berguna untuk sesi affinity, meski statelessness solusi yang lebih baik).

03

Health Check

Apa yang terjadi saat server crash? Tanpa health check, load balancer round-robin terus mengirim request ke server mati, setiap pengguna ketiga mendapat error 502. Health check menyelesaikan ini dengan mekanisme sederhana: load balancer secara berkala mengirim request uji ringan (biasanya GET /health) ke tiap backend. Server yang mengembalikan 200 tetap di rotasi; yang gagal di-blacklist sampai pulih.

Fig 3 / Health checks: dead servers get blacklisted; pings continue until recovery

Endpoint health di Go

Go
// A production health check verifies downstream dependencies, not just "I'm alive."
http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
    checks := map[string]string{}

    if err := db.PingContext(r.Context()); err != nil {
        checks["database"] = "unreachable"
    } else {
        checks["database"] = "ok"
    }

    if err := rdb.Ping(r.Context()).Err(); err != nil {
        checks["redis"] = "unreachable"
    } else {
        checks["redis"] = "ok"
    }

    for _, v := range checks {
        if v != "ok" {
            w.WriteHeader(http.StatusServiceUnavailable)
            json.NewEncoder(w).Encode(checks)
            return
        }
    }
    json.NewEncoder(w).Encode(checks)
})
04

Read Replica

Scaling server aplikasi Anda mudah setelah Anda mengeksternalkan state. Scaling database-nya, jantung ber-state arsitektur Anda, lebih sulit. Pendekatan pertama dan paling umum adalah read replica.

Gagasannya: pertahankan satu database primer (master) yang menangani semua operasi tulis (INSERT, UPDATE, DELETE), dan satu atau lebih database replika yang memegang salinan data yang sama dan hanya melayani operasi baca (SELECT). Karena 70-90% lalu lintas SaaS khas adalah baca, replika menyerap mayoritas beban.

Fig 4 / Read replicas offload read traffic and reduce geographic latency

Masalah replication lag

Data yang ditulis ke primer harus menyebar ke replika, dan penyebaran butuh waktu, replication lag. Jika pengguna memperbarui namanya di primer dan langsung me-refresh (baca yang memukul replika), mereka mungkin melihat nama lama karena replika belum mengejar.

Solusinya meliputi: read-after-write routing: rutekan baca yang mengikuti tulis baru-baru ini ke primer alih-alih replika; jeda sadar-lag: tunda baca sampai replikasi dikonfirmasi; atau update optimistis sisi klien: tampilkan nilai baru secara lokal sebelum server mengonfirmasi.

05

Sharding & Partisi

Sharding (juga disebut partisi) berarti memecah satu tabel besar lintas banyak instance database fisik berdasarkan shard key. Alih-alih satu tabel orders dengan 10 miliar baris, Anda punya 12 shard, satu per bulan, masing-masing memegang sebagian data.

Sharding memecahkan dua masalah sekaligus: latensi query turun karena tiap shard memuat lebih sedikit baris untuk dipindai, dan throughput naik karena banyak instance database bisa melayani request secara paralel.

Fig 5 / Sharding divides one massive table across multiple database instances

Bagian tersulit sharding memilih shard key: kolom atau kriteria yang menentukan shard mana yang memegang tiap baris. Strategi umum meliputi berbasis waktu (tanggal order), geografis (region pengguna), atau berbasis hash (hash user ID modulo jumlah shard). Shard key yang buruk menciptakan "hot shard", partisi tidak seimbang tempat satu shard menerima lalu lintas tidak proporsional.

Kecuali Anda punya keahlian administrasi database yang dalam, jangan membangun infrastruktur replikasi atau sharding sendiri. Pakai penyedia terkelola. Tugas Anda memahami konsep ini cukup baik untuk mengonfigurasi dashboard penyedia, memilih region replika, frekuensi backup, dan strategi shard, bukan mengimplementasikan algoritmanya sendiri.

07

CDN & Kecepatan Cahaya

Cahaya bepergian lewat kabel fiber optik pada ±200.000 km/detik. Round trip dari Tokyo ke Virginia (US-East-1), ±20.000 km, makan minimal 100ms. Ini lantai fisika yang tidak bisa dikurangi optimasi kode apa pun. Dan 100ms hanya transit jaringan, tambah pemrosesan server, query database, dan serialisasi, totalnya gampang mencapai 500-800ms.

Content Delivery Network (CDN) menyelesaikan ini dengan menaruh konten ter-cache di edge node (juga disebut Point of Presence atau PoP) yang secara fisik dekat dengan pengguna. Alih-alih round trip 20.000 km, request bepergian 100-200 km, mengurangi latensi jaringan dari 100ms ke 2-3ms.

Tokyo -> Virginia: ~100ms   |   Tokyo -> Local CDN: ~2ms

Apa yang di-cache di CDN

Konten statis titik awal yang jelas: bundel JavaScript, CSS, file HTML, gambar, font, dan video. Ini hanya berubah saat deployment, menjadikannya sempurna untuk caching berumur panjang. Respons API juga bisa di-cache saat datanya relatif stabil, katalog produk, post blog, konfigurasi publik. Penyedia CDN seperti Cloudflare mendukung purging cache berbasis tag: saat data berubah, Anda meng-invalidate hanya entri yang terdampak.

CDN sebagai lapisan keamanan

CDN juga menyerap serangan DDoS. Penyerang yang membanjiri origin server Anda dengan lalu lintas dari ribuan bot bisa men-crash server Anda atau menaikkan tagihan autoscaling besar. Dengan CDN seperti Cloudflare di depan, lalu lintas didistribusikan ke jaringan global mereka, yang cukup besar menyerap bahkan serangan terabyte-per-detik, sementara deteksi otomatis memicu CAPTCHA dan memblokir IP mencurigakan sebelum lalu lintas mencapai origin Anda.

08

Edge Computing

CDN tradisional melayani file statis, tanpa pemrosesan, hanya "temukan file, kirim file". Edge computing menambah lapisan pemrosesan di node CDN: kode Anda berjalan di edge, dekat pengguna, sebelum (atau alih-alih) mencapai origin server Anda.

Kasus pakai

Autentikasi di edge: Alih-alih round trip 100ms ke origin hanya untuk memverifikasi sesi dan mengembalikan 401, edge node memvalidasi sesi dalam 2-3ms. Origin Anda hanya menerima request sah yang terautentikasi, mengurangi latensi dan beban. Lokalisasi: Edge node mendeteksi region dan bahasa pengguna, melayani versi Jepang situs Anda tanpa round trip ke origin. Routing request: Routing cerdas ke backend terdekat berdasarkan geografi.

Batasan

Lingkungan edge computing punya resource terbatas, biasanya 1 GB RAM, 1 core CPU, tanpa akses file system, tanpa socket TCP mentah. Cloudflare Workers memakai V8 isolate (mesin JavaScript Chrome) yang boot di bawah 1ms tapi hanya bisa menjalankan JavaScript/TypeScript. Batasan ini berarti edge computing melengkapi origin server Anda, ia tidak bisa menggantikannya untuk logika bisnis kompleks, operasi berat database, atau tugas berumur panjang.

Cloudflare Worker
// Edge authentication, runs in 2-3ms at the closest CDN node
export default {
  async fetch(request, env) {
    const sessionId = getCookie(request, "session_id");

    if (!sessionId) {
      return new Response("Unauthorized", { status: 401 });
    }

    // Check session in edge KV store (global, low-latency)
    const userId = await env.SESSIONS.get(sessionId);
    if (!userId) {
      return new Response("Unauthorized", { status: 401 });
    }

    // Authenticated -> forward to origin server
    request.headers.set("X-User-Id", userId);
    return fetch(request);
  },
};
09

Pemrosesan Asinkron & Antrean

Tidak setiap operasi menuntut pengguna menunggu selesainya. Pemrosesan asinkron mengidentifikasi tugas yang bisa terjadi di latar dan menggesernya ke message queue, drastis mengurangi latensi yang dirasakan pengguna.

Polanya

Anggap mengundang anggota tim: Anda memvalidasi request, menyimpan undangan ke database (100ms), lalu perlu mengirim email via penyedia eksternal (300ms). Pengguna tidak perlu menunggu email terkirim, mereka hanya butuh konfirmasi undangan tercatat. Jadi Anda mengembalikan 200 setelah tulis database, dan mendorong "kirim email" sebagai job ke antrean. Proses worker terpisah mengambil job dan menangani email secara asinkron.

Synchronous: 100ms (DB) + 300ms (email) = 400ms perceived
Async: 100ms (DB) + push to queue = 100ms perceived

Apa yang digeser

Email & notifikasi: pengguna tidak mengharapkan pengiriman instan. Pemrosesan gambar/video: encoding, resize, pembuatan thumbnail. Penghapusan akun: delete berantai lintas banyak tabel. Generasi laporan: agregasi data lintas jutaan baris. Pengiriman webhook: retry saat gagal tanpa memblokir request utama. Aturannya: jika pengguna tidak butuh hasilnya dalam respons HTTP yang sama, ia kandidat pemrosesan asinkron.

Background job dengan Go dan Redis

Go
import (
    "context"
    "encoding/json"
    "github.com/redis/go-redis/v9"
)

type EmailJob struct {
    To       string `json:"to"`
    Subject  string `json:"subject"`
    Template string `json:"template"`
}

// Producer: push job to queue (called from your API handler)
func EnqueueEmail(ctx context.Context, job EmailJob) error {
    data, _ := json.Marshal(job)
    return rdb.LPush(ctx, "queue:emails", data).Err()
}

// Consumer: runs as a separate process (or goroutine)
func EmailWorker(ctx context.Context) {
    for {
        result, err := rdb.BRPop(ctx, 0, "queue:emails").Result()
        if err != nil { continue }

        var job EmailJob
        json.Unmarshal([]byte(result[1]), &job)
        sendEmail(job)  // takes 300ms, but no user is waiting
    }
}

Background job dengan Python (Celery)

Python
from celery import Celery

app = Celery("tasks", broker="redis://localhost:6379/0")

@app.task(bind=True, max_retries=3)
def send_invitation_email(self, email: str, invite_url: str):
    try:
        email_provider.send(
            to=email,
            subject="You've been invited!",
            template="invite",
            context={"url": invite_url},
        )
    except Exception as exc:
        raise self.retry(exc=exc, countdown=60)

# In your API handler, returns instantly to the user
send_invitation_email.delay("user@example.com", "https://app.co/invite/abc")

10

Monolit vs Microservice

Monolit satu unit yang bisa di-deploy: autentikasi, pemrosesan order, notifikasi, pembayaran, semua di satu codebase, satu proses, satu deployment. Monolit sederhana dikembangkan, diuji, di-deploy, dan direfaktor. Anda bisa scaling horizontal monolit dengan menjalankan banyak instance di belakang load balancer.

Microservice memecah aplikasi menjadi layanan independen, masing-masing dengan codebase, deployment, dan sering database-nya sendiri. Mereka terutama soal scaling tim, bukan mesin.

Kapan monolit hancur

Kopling deployment: Dengan 200 developer di satu codebase, kerja yang belum selesai satu tim bisa memblokir deployment tim lain. Granularitas scaling: Anda tidak bisa scaling hanya modul pembayaran, Anda scaling seluruh monolit, membuang resource pada modul yang tidak butuh. Kunci teknologi: Setiap modul harus memakai bahasa dan runtime yang sama, bahkan saat bahasa berbeda akan jauh lebih baik untuk tugas spesifik (mis. Rust untuk pemrosesan gambar vs. Node.js untuk rendering markdown).

Apa biaya microservice

Latensi jaringan: Yang tadinya panggilan fungsi kini panggilan HTTP/gRPC lintas jaringan, lebih lambat dan bisa gagal. Kompleksitas debugging: Satu request pengguna bisa mengalir lewat 4+ layanan; debugging butuh distributed tracing lintas semuanya. Konsistensi data: Tiap layanan mungkin memiliki database sendiri, memperkenalkan replication lag dan masalah konsistensi eventual. Overhead operasional: Tiap layanan butuh pipeline CI/CD sendiri, monitoring, alerting, dan rotasi on-call.

Monolith: Choose When
  • Tim < 50-100 engineer
  • Satu stack teknologi cukup
  • Kebutuhan scaling seragam
  • Anda ingin kecepatan iterasi tinggi
  • Anda memulai produk baru
Microservices: Choose When
  • Tim > 100+ engineer dengan batas yang jelas
  • Modul berbeda butuh stack teknologi berbeda
  • Modul individual butuh scaling independen
  • Kecepatan deployment terblokir kopling
  • Anda punya keahlian sistem terdistribusi yang dalam
The cardinal rule

Microservice bukan optimasi performa. Mereka arsitektur organisasional untuk tim besar. Jika tim Anda kecil, microservice menambah kompleksitas masif tanpa manfaat sama sekali. Monolit yang di-scaling horizontal menangani jutaan pengguna, kebanyakan perusahaan tidak pernah melampaui satu.

11

Serverless Computing

Server tradisional selalu menyala: Anda menyediakan mesin (mis. 4 GB RAM, 2 core) dan membayarnya 24/7, entah ia menangani 500 RPS atau nol. Anda harus memprediksi kapasitas: under-provision dan pengguna dapat error saat lonjakan lalu lintas; over-provision dan Anda membuang uang.

Serverless membalik model ini: Anda memberi kode (fungsi), dan platform menyediakan mesin hanya saat request tiba. Setelah respons dikirim, mesin mungkin di-daur ulang. Anda membayar hanya untuk milidetik eksekusi CPU aktual, bukan waktu idle.

Cara kerjanya

API Gateway menerima request HTTP dan merutekan tiap ke fungsi serverless. Pada request pertama, platform men-boot runtime, memuat kode Anda, memproses request, dan mengembalikan respons. Instance mungkin tetap hangat beberapa detik (menangani request berikutnya tanpa cold start) atau dihancurkan. Scaling otomatis dan secara teori tanpa batas, platform membuat instance sebanyak yang dibutuhkan.

Masalah cold start

Menyalakan environment eksekusi baru, men-boot OS/VM, memuat runtime bahasa, memuat kode Anda, makan waktu. Inilah cold start, dan ia kelemahan utama serverless. Cold start bervariasi dramatis tergantung teknologi:

PlatformTeknologiCold Start
Cloudflare WorkersV8 Isolate (JavaScript)±0-5ms
AWS Lambda (Node.js)microVM Firecracker±100-300ms
AWS Lambda (Java)Firecracker + JVM±1-3 detik
AWS Lambda (Python)Firecracker + CPython±200-500ms

Kapan memakai serverless

Good Fit
  • Tugas digerakkan peristiwa (pemrosesan upload file, consumer antrean)
  • Lalu lintas sporadis, tidak terprediksi
  • Pipeline pemrosesan gambar/video
  • Job terjadwal (tugas mirip cron)
  • Autentikasi & routing di edge
Bad Fit
  • API sensitif latensi (perbankan, pembayaran)
  • Proses berumur panjang (>15 menit di Lambda)
  • Aplikasi berat WebSocket
  • Aplikasi yang butuh banyak koneksi DB persisten
  • Lalu lintas stabil volume tinggi yang terprediksi
The honest take

Serverless kuat untuk kasus spesifik tapi bukan pengganti universal untuk server. Industri agak over-hyped. Server tradisional dengan autoscaling tetap pilihan tepat untuk kebanyakan SaaS dengan lalu lintas stabil. Serverless bersinar untuk beban kerja digerakkan peristiwa dan sporadis tempat Anda sebaliknya membayar komputasi idle.

Sum

Model Mental Scaling

Setelah mencakup lanskap penuh, dari persentil latensi lewat sharding database, CDN, pemrosesan asinkron, microservice, dan serverless, ini model mental yang mengikat semuanya:

1. Selalu mulai dari masalah

Setiap teknik di catatan ini adalah solusi. Sebelum meraih solusi, ukur sistem Anda memakai observabilitas (log, metrik, trace). Ketahui secara spesifik komponen mana yang lambat, kenapa lambat, dan seberapa lambat. Memecahkan masalah yang salah lebih buruk daripada tidak melakukan apa pun, ia memberi kepercayaan palsu sementara bottleneck sebenarnya membusuk.

2. Prefer solusi sederhana

Monolit yang di-scaling vertikal lebih sederhana daripada mesh microservice yang di-scaling horizontal. Indexing database yang tepat lebih sederhana daripada menambah cache Redis. Solusi sederhana lebih mudah dipahami, di-debug, dan dioperasikan. Kompleksitas adalah biaya, setiap komponen yang Anda tambah adalah komponen lain yang bisa gagal, harus dipantau, harus dipahami. Terima kompleksitas hanya saat kesederhanaan benar-benar tidak cukup.

3. Scale untuk masalah yang Anda miliki

Anda tidak perlu membangun untuk sejuta pengguna di hari pertama, kebanyakan platform tidak pernah mencapai sejuta pengguna. Bangun untuk skala Anda saat ini dengan ruang kepala wajar, dan biarkan observabilitas memberi tahu Anda kapan dan di mana berinvestasi scaling. Aplikasi Anda punya karakteristik unik yang mungkin tidak berlaku saran generik dari blog engineering Netflix. Belajar dari perilaku sistem Anda sendiri.

4. Ukur sejak hari pertama

Observabilitas satu-satunya pengecualian dari "mulai sederhana". Logging, metrik, dan tracing level produksi harus ada sejak deployment pertama. Mereka membayar diri seketika, you tidak pernah harus menebak di mana bug, tidak pernah dikejutkan lonjakan lalu lintas, dan selalu punya data untuk keputusan scaling yang terinformasi.

Go
// A minimal but real observability setup: Prometheus metrics + structured logging
import (
    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promhttp"
    "log/slog"
)

var requestDuration = prometheus.NewHistogramVec(
    prometheus.HistogramOpts{
        Name:    "http_request_duration_seconds",
        Help:    "Duration of HTTP requests",
        Buckets: prometheus.DefBuckets,
    },
    []string{"method", "path", "status"},
)

func init() {
    prometheus.MustRegister(requestDuration)
}

// Expose /metrics for Prometheus to scrape
// Visualize in Grafana: p50, p90, p99 latency per endpoint
http.Handle("/metrics", promhttp.Handler())

5. Performa adalah pola pikir

Scaling bukan proyek sekali jalan. Ia praktik berkelanjutan, Anda membangun sistem, melihatnya berjuang di bawah lalu lintas nyata, mengoptimalkan yang penting, dan belajar yang tidak. Seiring waktu, lewat coba-coba, Anda mengembangkan intuisi di mana bottleneck bersembunyi dan solusi mana yang benar-benar menggerakkan jarum. Tugas Anda bukan memprediksi setiap kegagalan, tapi membangun sistem yang menangani kegagalan dengan anggun dan mengembangkan keterampilan diagnostik untuk menyelesaikannya cepat saat terjadi.

The Scaling Playbook, In Order

Langkah 1: Ukur semuanya (observabilitas sejak hari pertama). Langkah 2: Perbaiki database (index, N+1, connection pooling). Langkah 3: Tambah caching (Redis untuk jalur panas). Langkah 4: Geser kerja (pemrosesan asinkron untuk email, upload, delete). Langkah 5: Pakai CDN (konten statis + caching respons API). Langkah 6: Vertical scaling (mesin lebih besar, tanpa perubahan kode). Langkah 7: Horizontal scaling (server stateless + load balancer). Langkah 8: Scaling database (read replica, lalu sharding jika perlu). Langkah 9: Baru setelah itu pertimbangkan microservice, serverless, atau edge computing.
